## 1. Packet capture

### Wireshark GUI workflow

1. Select the correct interface (`Capture → Options`).
2. Enable **promiscuous mode** only when authorized to sniff all LAN traffic.
3. Prefer capturing everything, then filter during analysis (display filters are more flexible than capture filters).
4. Save as `.pcapng` with a timestamped filename for chain of custody.

| Setting | Recommendation |
| --- | --- |
| Capture filter | Use sparingly — e.g. `host 192.0.2.10` for scoped IR |
| Ring buffer | Enable for long-running monitoring |
| Time display | Switch to **UTC** for multi-timezone investigations (`View → Time Display Format`) |
| Name resolution | Disable during capture; resolve IPs afterward to avoid DNS leakage |

### TShark capture commands

```bash
# List interfaces
tshark -D

# Capture 100 packets on eth0
tshark -i eth0 -c 100 -w incident.pcapng

# Capture filter (BPF) — port 443 only
tshark -i eth0 -f "tcp port 443" -w https.pcapng

# Read and summarize
tshark -r incident.pcapng -q -z io,phs
```

### Capture vs display filters

| Type | When set | Syntax | Example |
| --- | --- | --- | --- |
| **Capture filter** (BPF) | Before capture | `host`, `net`, `port`, `tcp`, `udp` | `tcp port 80` |
| **Display filter** | During analysis | Wireshark field expressions | `http.request.method == "GET"` |

Capture and display filters use **different syntax** — you cannot paste one into the other.

## 2. Display filters

Display filters reduce visible packets without deleting underlying capture data. Filters are lowercase; Wireshark shows green (valid), red (invalid), or yellow (unreliable).

### Operators

| Operator | Meaning | Example |
| --- | --- | --- |
| `==` | Equal | `ip.addr == 192.0.2.10` |
| `!=` | Not equal | `ip.src != 10.0.0.1` |
| `>`, `<`, `>=`, `<=` | Comparison | `ip.ttl < 64` |
| `&&`, `\|\|`, `!` | AND, OR, NOT | `(tcp.port == 443) && (ip.src == 192.0.2.5)` |
| `contains` | Substring (case-sensitive) | `http.host contains "admin"` |
| `matches` | Regex | `http.host matches "\.(php\|asp)$"` |
| `in` | Set membership | `tcp.port in {80 443 8080}` |

### Essential filter reference

| Goal | Display filter |
| --- | --- |
| All traffic to/from host | `ip.addr == 192.0.2.10` |
| Outbound only | `ip.src == 192.0.2.10` |
| TCP port 443 | `tcp.port == 443` |
| DNS queries | `dns.flags.response == 0` |
| DNS responses | `dns.flags.response == 1` |
| HTTP GET requests | `http.request.method == "GET"` |
| HTTP 4xx/5xx responses | `http.response.code >= 400` |
| TLS Client Hello (SNI) | `tls.handshake.type == 1` |
| SYN packets only | `tcp.flags.syn == 1 && tcp.flags.ack == 0` |
| RST packets | `tcp.flags.reset == 1` |

### GUI filter shortcuts

* **Right-click field → Apply as Filter** — instant filter from a packet value
* **Analyze → Follow → TCP/UDP/HTTP Stream** — reconstruct application data (auto-applies stream filter)
* **Statistics → Protocol Hierarchy** — see protocol mix; right-click to filter
* **Statistics → Conversations / Endpoints** — identify top talkers

Save frequently used filters as **bookmarks** or **filter buttons** on the toolbar.

### TShark filtering

```bash
# Display filter while reading
tshark -r capture.pcapng -Y 'http.request.method == "POST"'

# Capture filter + display filter combined
tshark -i eth0 -f "tcp port 80" -Y 'http.response.code == 404' -c 50

# Export matching packets to new file
tshark -r capture.pcapng -Y 'dns.qry.name contains "evil"' -w dns-suspect.pcapng
```

## 3. Protocol analysis

### HTTP / HTTPS

| Analysis step | Action |
| --- | --- |
| Find requests | `http.request` |
| Inspect headers | Expand HTTP layer → look at `User-Agent`, `Host`, `Cookie` |
| Reconstruct session | Follow → HTTP Stream |
| Extract files | `File → Export Objects → HTTP` (lab artifacts only) |

```bash
# TShark HTTP statistics
tshark -r capture.pcapng -q -z http,tree
```

For encrypted HTTPS, look at **TLS Client Hello** for SNI (`tls.handshake.extensions_server_name`) — payload remains encrypted without session keys.

### DNS

| Filter | Purpose |
| --- | --- |
| `dns` | All DNS traffic |
| `dns.qry.name contains "suspicious"` | Hunt for known-bad domains |
| `dns.flags.response == 0` | Queries only |
| `dns.qry.type == 1` | A record lookups |

Use **Statistics → DNS** for query/response breakdown. High query volume to a single domain from one host may indicate tunneling (see [Detection](#4-defensive-detection-patterns)).

### TCP / UDP fundamentals

| Observation | Filter / technique |
| --- | --- |
| Three-way handshake | `tcp.flags.syn == 1` then SYN-ACK, ACK sequence |
| Connection teardown | `tcp.flags.fin == 1` or `tcp.flags.reset == 1` |
| Retransmissions | Expert Info → warn; or `tcp.analysis.retransmission` |
| UDP service probe | `udp` + ICMP type 3 code 3 (port unreachable) |

### Expert Info severity

| Colour | Meaning | Action |
| --- | --- | --- |
| Blue (Chat) | Normal workflow | Informational |
| Cyan (Note) | Notable event | Review context |
| Yellow (Warn) | Unusual condition | Investigate if clustered |
| Red (Error) | Malformed / checksum fail | Possible corruption or attack |

## 4. Defensive detection patterns

Use these hunt filters after baselining normal traffic on your network.

### Nmap scan recognition

Pair with [Nmap Scanning Guide](/notes/networking/nmap-scanning-guide) — know what your own scans look like before alerting on others.

| Scan type | Pattern | Display filter |
| --- | --- | --- |
| TCP connect (`-sT`) | Full handshake, window often > 1024 | `tcp.flags.syn == 1 && tcp.flags.ack == 0 && tcp.window_size > 1024` |
| SYN stealth (`-sS`) | SYN without completing handshake, window ≤ 1024 | `tcp.flags.syn == 1 && tcp.flags.ack == 0 && tcp.window_size <= 1024` |
| UDP scan | UDP probe + ICMP port unreachable | `icmp.type == 3 && icmp.code == 3` |

**Hunt tip:** Look for a single source IP sending SYN packets to many destination ports in a short window:

```
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

Then pivot with **Statistics → Conversations → TCP** to identify the scanner.

### ARP spoofing / MITM indicators

ARP has no authentication — gratuitous ARP replies are a common spoofing signal.

| Indicator | What to check |
| --- | --- |
| Duplicate IP → MAC mappings | `arp` filter; same `arp.src.proto_ipv4` with different `arp.src.hw_mac` |
| Gratuitous ARP flood | Unsolicited ARP replies (`arp.opcode == 2`) at high rate |
| Gateway MAC change | Compare current ARP table to baseline |

Filter: `arp` — sort by IP and verify one MAC per IP.

### DNS tunneling and C2 beacons

| Signal | Filter / technique |
| --- | --- |
| Long subdomain labels | `dns.qry.name matches "[a-z0-9]{30,}"` |
| High query rate to one domain | Statistics → DNS → filter domain |
| TXT record exfil | `dns.qry.type == 16` |
| Regular interval traffic | `Statistics → IO Graph` per IP |

Correlate with endpoint data from [Essential Linux Commands](/notes/linux/essential-linux-commands-for-cybersecurity-specialists) (`ss -tnp`).

### Suspicious HTTP user agents

Scanner and tool fingerprints often appear in the `User-Agent` header:

```
http.user_agent contains "Nmap" ||
http.user_agent contains "sqlmap" ||
http.user_agent contains "Nikto" ||
http.user_agent contains "curl/" ||
http.user_agent matches "(?i)bot|crawler|scanner"
```

Validate against known internal scanners before escalating.

### Credential and data exposure

When analyzing **authorized lab captures** with cleartext protocols:

* Follow HTTP streams for plaintext credentials (legacy apps)
* Check `ftp`, `telnet`, `smtp` for unencrypted auth
* Export Objects only in controlled IR — treat extracted files as potentially malicious

## TShark quick reference

| Task | Command |
| --- | --- |
| Protocol hierarchy | `tshark -r file.pcapng -q -z io,phs` |
| Top talkers (endpoints) | `tshark -r file.pcapng -q -z endpoints,ip` |
| TCP conversations | `tshark -r file.pcapng -q -z conv,tcp` |
| Expert summary | `tshark -r file.pcapng -q -z expert` |
| JSON output | `tshark -r file.pcapng -T json > output.json` |
| Field extract | `tshark -r file.pcapng -T fields -e ip.src -e ip.dst -e tcp.port` |

### Profiles and workflow tips

* Create **Wireshark profiles** per investigation type (malware, scan hunt, web app) with saved filters and colouring rules.
* Document capture start/stop time, interface, and filter in your IR notes.
* Chain captures: full PCAP → filtered subset → exported objects.

## Best practices

* Capture to write-once media or WORM storage for legal hold scenarios.
* Sync clocks (NTP) across capture host and endpoints for timeline correlation.
* Disable name resolution during live capture to avoid polluting evidence with external DNS.
* Treat Expert Info warnings as leads, not confirmed incidents.
* Pair packet evidence with [Windows Event Log Analysis](/notes/windows/windows-event-log-analysis-advanced-threat-detection-guide) for host-side confirmation.
