Test only targets explicitly listed in program scope. Out-of-scope testing, credential stuffing on production accounts, and denial-of-service attempts violate most policies and may be illegal.

## 1. Pre-engagement checklist

| Step | Action |
| --- | --- |
| Read scope | Confirm domains, mobile apps, APIs, and excluded assets |
| Note rules | Check prohibited tests (DoS, social engineering, physical access) |
| Set up lab | Isolated VM or VPS; separate browser profile for Burp |
| Enable logging | Export Burp logs; timestamp every finding |
| Define exit criteria | Stop when out of scope or when impact is unclear |

## 2. Platform and target selection

| Platform | Strengths | Watch for |
| --- | --- | --- |
| [HackerOne](https://www.hackerone.com) | Large enterprise programs, clear disclosure | Competitive triage queues |
| [Bugcrowd](https://www.bugcrowd.com) | Broad program mix, VDP options | Variable payout timelines |

**Target selection heuristics:** prefer programs with recent payouts, responsive triage, and narrow scope you understand (e.g. single SPA + API). Avoid stale programs with no resolved reports in 90+ days unless you are learning recon only.

## 3. Recon workflow

```text
Scope asset list → subdomain enum → live host probe → port/service map → crawl → parameter inventory
```

| Phase | Tools | Hub reference |
| --- | --- | --- |
| Subdomain discovery | subfinder, amass | [Kali Toolkit](/notes/linux/kali-linux-toolkit-guide) |
| Port scan | nmap | [Nmap Guide](/notes/networking/nmap-scanning-guide) |
| HTTP probe | httpx, katana | Kali Toolkit |
| Template scan | nuclei | [Nuclei & Burp Templates](/notes/web/nuclei-plugin-burp-suite-template-creation-guide) |
| Traffic review | Burp Suite, Wireshark | [Wireshark](/notes/networking/wireshark) |

Document every hostname and path before intrusive testing. Remove out-of-scope assets from your target list immediately.

### Cloud and secrets

* Search public repos and paste sites for leaked keys (authorized OSINT only).
* Review S3/GCS bucket naming patterns when cloud assets are in scope.
* Validate finding impact in a staging replica — never exfiltrate production PII.

## 5. Burp Suite hygiene

* Use separate projects per program to avoid cross-contamination.
* Enable logging; export HTTP history for reports.
* Scope filter: restrict site map to in-scope hosts only.
* Disable live scanning on production during business hours if program rules require it.

## 6. Reporting template

Every valid report should include:

1. **Title** — vulnerability class + affected asset
2. **Severity** — CVSS 3.1 vector with justification
3. **Asset** — URL, parameter, or endpoint
4. **Steps to reproduce** — numbered, minimal, copy-paste requests
5. **Impact** — what an attacker gains (data, account, RCE)
6. **Remediation** — specific fix, not generic advice
7. **Evidence** — redacted screenshots or HTTP transcripts

## 7. Knowledge base maintenance

| Source | Use for |
| --- | --- |
| NVD / CVE feeds | New CVE workflow on in-scope stacks |
| Vendor advisories | Patch-diff hunting on known products |
| Program changelogs | Scope updates and new assets |

## Best practices

* One finding per report unless chained impact is clearly documented.
* Do not retest fixed issues on production without permission.
* Respect rate limits; throttle scans and fuzzers.
* Pair offensive findings with defensive detection ideas for higher-quality reports.
